# ELIAS NET Capabilities 區段顧問評估與改版決議

## 一、評估範圍

本次評估針對 ELIAS NET 首頁 `#capabilities` 區段。現有內容已具備策略、體驗、資料、AI 夥伴、整合與治理六項能力，也有互動式圖像與進階說明；問題不在能力不足，而在一般訪客第一眼仍可能把它理解成技術服務清單，尚未立即看見「ELIAS NET 如何進入一個真實工作、何時協助、何時停下、最後由誰負責」。

因此本次改版將 capabilities 定義為一條**可被理解、可被核准、可被追蹤的 AI 工作路徑**，並把技術能力放在第二層說明。第一層先用工作語言讓非技術人員理解，第二層再提供資料、權限、整合、Agent、紀錄與驗證的深入資訊。

## 三、三種董事會思維模型的判定

**Steve Jobs 型產品體驗**會刪掉首頁不必要的術語，要求訪客在第一眼理解：「這是一套把 AI 放進工作的方式，而不是一組炫技動畫」。因此六項能力應保留，但每項先用生活化的工作語言命名，技術細節放在展開區。

**Elon Musk 型第一性原理**會把問題拆成最小可驗證單位：工作問題、核准資料、允許的 AI 協助、人工確認、結果與證據。Capabilities 的主視覺因此應從抽象能量流改成可讀的工作路徑，並保留明確的停止點。

**Mark Zuckerberg 型平台與成長思維**會檢查能力能否被不同部門重複使用，並形成「工作問題 → Pilot → 回饋 → 改善 → 擴大」的循環。因此本區段需要連接五大產品領域與導入方法，而不是只列一次性的技術能力。

## 四、實作決議

1. 將區段主標改為「從一個工作問題，到一個有責任的 AI 工作方式」，英文對應為 `From one work problem to an AI-enabled way of working with accountability.`
2. 保留六項能力卡片，但將六項能力的第一層命名改為「從問題找起、把 AI 放進流程、整理可信資料、建立有界線的 AI 協助、接上原本的工具、把規則寫進工作」。
3. 在主視覺加入白話路徑：`工作問題 → 核准資料 → AI 協助 → 人的確認 → 可追蹤結果`。技術 SVG 與 Canvas 仍可保留作為視覺層，但所有關鍵節點必須有 HTML 文字。
4. 每張能力卡必須可回答四個問題：現在卡在哪裡、ELIAS NET 協助哪一步、誰負責確認、最後留下什麼結果。現有展開式細節保留，並提高「我們如何協助」與「最後形成」的可讀性。
5. 將「展開技術與治理能力」留在第二層，避免非技術訪客一進入 capabilities 就被 API、Agent、索引或模型選擇阻擋。
6. 動畫採用節點沿路徑出現、卡片依序揭示與輕微視差，不新增持續旋轉或高耗能效果；reduced motion 時直接顯示所有文字與節點。
7. Capabilities 必須與五大產品領域相互連結：醫療與照護看重資料與專業確認；AI 防護看重權限與停止；關鍵任務看重資訊集合與授權；企業知識看重來源與交接；多模態資訊看重格式整理與驗證。

## 五、驗收門檻

改版後必須在繁中、簡中與英文首頁通過下列檢查：主標可在十秒內理解、五步工作路徑可用文字讀取、六張能力卡存在、展開／收合可鍵盤操作、所有 SVG 與 Canvas 失效時仍有文字、`prefers-reduced-motion` 不會隱藏內容、手機不橫向溢出、沒有重複 ID、沒有破損錨點或缺少資產，且 `npm run check`、`npm run build`、`npm run qa:static` 全部通過。
